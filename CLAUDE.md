## Product
EAMI — **Enterprise AI Monitoring & Intelligence**: an on-prem/SaaS hybrid platform that (a) discovers AI tooling on employee endpoints and (b) governs AI agent tool calls through a policy-enforcing MCP gateway, with audit logging, human-approval escalation, FinOps token-spend tracking, and episode/memory recall.

## Architecture (see `ARCHITECTURE.md` for full detail — still accurate, not legacy)
Five Go services (Go 1.25, one `go.work` workspace) + one React SPA:
- `eami-agent` — Windows/macOS/Linux endpoint scanner (12 detection domains), ships reports to the collector.
- `eami-collector` — on-prem ingest server, SQLite write-ahead buffer, forwards to `eami-api`.
- `eami-gateway` — MCP proxy: policy enforcement, approval routing, audit writing, episode recording, JWT agent identity.
- `eami-policy` — policy library (structural rules real; semantic/LLM rules stubbed, see `BUILT.md`).
- `eami-api` — SaaS REST backend (Chi router), Postgres (pgvector + TimescaleDB), serves `eami-ui`.
- `eami-ui` — React 18 + TS + Vite SPA, TanStack Query, generated OpenAPI client.

Contract: `api/openapi.yaml` (owned by Architect-EAMI per `BOUNDARIES.md`). DB: `schema/schema.sql` + `schema/migrations/001`–`007`.

## Conventions
- **Naming:** Go — standard `internal/<domain>/` package layout, one file per concern; sqlc-style `*.sql.go` in `eami-api/internal/store`. TS — `PascalCase` components, `useX.ts` resource hooks in `src/hooks/`, pages under `src/pages/<section>/`.
- **Error handling (Go):** wrap and return errors up to the HTTP handler layer; handlers call `writeError(w, status, code, msg)`. No panics for expected failures.
- **Frontend API access:** only through the generated client / `apiFetch()` in `src/api/client.ts` — no raw `fetch`/`axios` in components (documented escape hatch exists in `client.ts` for endpoints not yet in the OpenAPI spec).
- **Commit format:** Conventional-commit-ish — `type: summary` or `type(scope): summary`. Types observed: `fix`, `chore`, `wip`. Reference B-IDs in commit messages once B-numbered work starts.
- **Test frameworks:** Go — stdlib `testing`, table-driven. Frontend — **none configured yet** (`tsc --noEmit` / `type-check` only; no vitest/jest/playwright present despite `BOUNDARIES.md` assigning that ownership to QA-EAMI — see `BACKLOG.md`).
- **Real-Postgres Go test pool lifecycle — mandatory pattern, not a style preference:** always close the pool via `t.Cleanup(func() { pool.Close() })`, registered *before* any other `t.Cleanup` that touches the database (e.g. a per-org `DELETE`). **Never** write a plain `defer pool.Close()` in a real-Postgres test file, even though pairing it with a plain `defer pool.Exec(...DELETE...)` (not `t.Cleanup`) is technically safe under Go's LIFO defer ordering — that second, differently-safe pattern is exactly what caused this rule to exist: `defer` and `t.Cleanup` are two different teardown phases (`t.Cleanup` callbacks all run *after* every one of a function's own `defer`s has already unwound), so mixing a plain `defer pool.Close()` with *any* `t.Cleanup`-registered cleanup silently closes the pool before that cleanup can run — a real DELETE errors out silently, and the seeded org/rows leak into whichever Postgres the test ran against. **This exact bug has independently recurred three times in three different files in one session** (`paste_events_test.go`, logged as B-056; `eami-api/internal/api/workflows_test.go`, twice — once in the file's first draft, once again in a sibling `workflow_step_params_test.go` written the same session after the first fix was already known) — each time caught only by noticing leaked orgs in the shared dev database after the fact, never by a compiler or `go vet`. Knowing about the bug did not prevent rewriting it; only always using the same one pattern will. When writing a new real-Postgres test file, copy the pool-setup block from `eami-api/internal/api/workflows_test.go`'s `newWorkflowTestEnv`-style helpers or `eami-gateway/internal/workflow/testenv_test.go`'s `newWorkflowTestEnv` (both `t.Cleanup`-only, both correctly ordered) — do not copy `tools_update_pg_test.go`'s older plain-`defer`-pair style, which remains correct in place but is no longer the template to extend.
- **Pluggable backend types (connectors/providers):** when adding a new backend *type* behind an existing dispatch surface — a new AI provider, a Skill, an A2A agent, or anything else structurally similar — follow the `aiprovider.Adapter` pattern (`eami-gateway/internal/aiprovider/types.go`, `router.go`), established B-057 and unchanged since: define a small interface (`Adapter`: `Provider() string`, `Dispatch(ctx, creds, req) (Response, error)`), implement it in one new file per backend (`claude.go` is the reference instance — `ClaudeAdapter`), and register the instance in an explicit `map[string]Adapter` passed to the router's constructor (`aiprovider.New(...)`, wired from `cmd/gateway/main.go`'s `aiProviderRegistry`) — never a global or `init()`-time registration. This is a different problem from B-102's dispatch-hook mechanism (`cmd/gateway/dispatcher.go`): a new *type* behind the dispatch surface, not a new cross-cutting reaction to an existing call — don't conflate the two when scoping a future brief.
