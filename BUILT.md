## eami-agent
**Purpose:** Lightweight endpoint scanner (Windows primary, macOS/Linux ports per ADR-015). Runs on interval, detects AI tooling footprint, ships JSON reports to the collector.
**Status:** STABLE (core), WORKING-BUT-FRAGILE (Linux DNS correlation, macOS — no test hardware).
**Key files:** `cmd/agent/main.go`; `internal/detection/{ai_apps,ai_processes,browser,cloud_clients,file_changes,gpu,mcp_servers,models,network_activity,nodejs_ai,python_envs,scheduled_tasks}/`; `internal/{payload,collector,config,service}/`; `internal/{nativemsg,nmregister,nmlauncher}/` (B-034, native messaging host).
**Interfaces:** `POST <collector-url>/ingest` — gzipped JSON `Report{}` (endpoint id, hostname, per-detection-domain findings), API-key header auth. `eami-agent --native-messaging-host` (B-034) — browser native-messaging host mode, stdin/stdout, no live caller yet (no B1 extension).
**Data owned:** none (stateless scanner; report shape defined by `internal/payload`).
**Test coverage:** 5 `_test.go` files vs 55 source files (~11:1 file ratio). Not executed this session.
**Known limitations:**
- `internal/detection/network_activity/scanner_linux.go:181` — `linuxDNSCache()` runs `resolvectl statistics` but discards output, always returns `nil` (comment: "resolvectl doesn't expose individual hostnames"). DNS-hit correlation unimplemented on Linux; rest of network scanner (proc-based connection mapping) is real.
- macOS build path exists (ADR-015) but has never run on real macOS hardware — `.pkg` install/uninstall smoke test deferred per `tasks/TASK-054-results.md`.
- Scheduled-tasks scanner exists (`internal/detection/scheduled_tasks/`) despite `ROADMAP.md` listing it as "deferred to v1.1" — it shipped early.

**Interfaces — B-034 (2026-07-26), native-messaging host for real-time paste-event relay:** new `eami-agent --native-messaging-host` mode so a future browser extension (B1, not built yet) can hand off captured paste events in real time over stdin/stdout, using the browser's standard length-prefixed-JSON native messaging protocol — not a network port (smaller attack surface, no listening socket, standard per-browser registration). Zero changes to any existing scanner or the poll loop: this mode is a wholly separate process invocation (`main.go` dispatches straight to it and returns before `runLoop` is ever reached).
**Identity finding that shaped the design:** investigated where `eami-agent` stores its registered identity, per this task's explicit instruction to verify rather than assume — found `eami-agent` has **no `org_id` anywhere** (config, report payload, or remote-config response), only `agent_id` (local config, defaults to hostname). `org_id` is resolved entirely server-side today. Combined with `eami-collector`/`eami-api`/B-032's ingestion endpoint all being frozen for this task, paste events are forwarded via the **existing** `collector.Sender.Send()` — immediately, out-of-band from the 5-minute poll cycle, not invented as a new direct link to the backend. Today this lands in the existing agent-report pipeline's raw JSON blob (not literally in B-032's `paste_events` table yet) — completing that server-side wiring is logged as a new follow-up, B-035 (see `BACKLOG.md`), not silently left undone.
**New packages:**
- `internal/nativemsg` — the protocol: `readMessage`/`writeMessage` (4-byte little-endian length prefix + JSON, capped at 1MB — rejected before any allocation, guarding against a hostile/malformed length value), `PasteEventMessage` (no field can carry raw pasted text, mirrors B-032's guarantee), `RunHost` (the message loop, per-message panic recovery via `handleOne` so one bad message can't crash the process — B-027's discipline, including the stack-trace-in-log convention that a code-review pass caught missing from the first version and this session fixed).
- `internal/nmregister` — Windows: writes a native-messaging manifest and points Chrome's/Edge's `NativeMessagingHosts` registry keys at it. `AllowedExtensionID` is a literal `PLACEHOLDER_EXTENSION_ID_REPLACE_AFTER_B1` — there is no B1 yet, so this manifest cannot be matched by any real extension origin until that placeholder is replaced, the correct default for a not-yet-existing caller. Non-Windows: a stub directing to the shell-script-based registration instead (no registry involved on those platforms).
- `internal/nmlauncher` — defense-in-depth parent-process verification (see security-review section below).
**Real bug caught and fixed by this session's own testing, before it could ever reach a real browser:** the native-messaging manifest's `"path"` originally pointed straight at `eami-agent.exe`/`eami-agent`. Chrome/Edge's manifest schema has no `args` field — the browser execs whatever `path` names with only its own fixed arguments, never anything the manifest supplies — so a real browser would have launched the real binary with **no** `--native-messaging-host` flag at all, silently falling through to the ordinary poll loop instead of acting as a host. Caught by the mandatory code-review pass, not by any test in the original changeset (every test explicitly passed the flag on the command line itself, masking the gap). Fixed with a launcher indirection: `nmregister.Install` (Windows) and the Linux/macOS postinstall scripts now create a **hard link** (not a copy — same file, zero extra disk space, can't fall out of sync on upgrade) named `eami-agent-nmhost`/`eami-agent-nmhost.exe` next to the real binary, and the manifest's `"path"` points at that name instead. `cmd/agent/main.go`'s `invokedAsNativeMessagingLauncher()` detects invocation under that name (checking both `os.Args[0]` and the resolved `os.Executable()` path) and behaves exactly as if `--native-messaging-host` had been passed explicitly. Live-verified end-to-end after the fix: built the real binary, ran `--register-native-messaging install`, confirmed the hard link + manifest + both registry keys are correct, then invoked `eami-agent-nmhost.exe` with **no explicit flag** and confirmed it entered host mode, correctly parsed a real length-prefixed message, and forwarded it to a mock collector — proving the actual real-world browser-invocation path, not just the flag-based shortcut every automated test uses.
**Second real bug caught by this session's own testing:** adding the parent-process-check log line (below) surfaced that `main.go`'s logger wrote to `os.Stdout` — the exact stream the native messaging protocol uses for length-prefixed framing. Any log line (a warning, an error, or this new info line) interleaved with protocol bytes desyncs the browser's parsing with no way for the reader to distinguish log text from a length prefix. This was a **latent bug in the original implementation too** (RunHost's own `log.Warn`/`log.Error` calls on malformed input or a forwarding failure), just not triggered by earlier tests, which happened not to exercise those exact log-emitting paths at the subprocess level. Fixed: `main.go` now routes all logging to `os.Stderr` specifically in `--native-messaging-host` mode (every other mode keeps logging to stdout unchanged). New regression test (`TestNativeMessagingHost_LoggingNeverCorruptsStdout`) sends a malformed length prefix (the exact case that logs a warning) and asserts stdout still parses as a clean, correctly-framed response while the warning appears on stderr.
**Security review finding, fixed (confused-deputy telemetry forgery):** the mandatory security review found that nothing prevented an arbitrary local process from invoking `--native-messaging-host` directly and having it forward fabricated paste-event data using the agent's own already-configured collector API key — native messaging's `allowed_origins` restriction is enforced by the browser before it launches the host, not by the host process itself, so it provides no protection against direct invocation of the binary. Fixed with `internal/nmlauncher.VerifyLaunchedByBrowser()`: checks the immediate parent process (Windows via a `CreateToolhelp32Snapshot` walk — live-verified against this machine's real process tree, correctly resolving `go.exe` as the parent during `go test`; Linux via `/proc/<ppid>/exe`; macOS via `ps -o comm=` — neither of the latter two exercised on a live host this session, this machine is Windows). Policy: if the parent can't be determined at all, **fails open** with a loud warning (an inconclusive check must not break the feature entirely); if it can be determined and isn't a recognized browser, **fails closed**. `EAMI_NM_SKIP_PARENT_CHECK=1` is a documented operator override (same fail-closed-with-escape-hatch convention as B-023's SSRF guard, B-025's secret validation) — explicitly **not** a bulletproof fix (a capable local attacker could rename their process or launch as a child of a real browser), but a meaningful defense-in-depth improvement over no check at all.

## eami-browser-extension
**Purpose:** Manifest V3 Chrome/Edge extension (B1) — the browser-side half of the paste-detection epic (B-032 backend, B-034/B0 native-messaging host, this task). Detects paste events on 6 known AI-tool web UIs and relays destination-domain/timestamp/content-length/content-hash to B0 via native messaging. Known-destination detection only, no content classification/DLP.
**Status:** STABLE, first version, **fully manually verified** (2026-08-03) — all 5 steps of `MANUAL_TESTING.md` passed live, by the user personally, on a real Chrome/Edge install (extension ID confirmed correct, scoped permissions confirmed, paste capture + no-raw-content confirmed on an allowlisted domain, non-allowlisted domain confirmed silent, service-worker-restart durability confirmed, and `flush()` confirmed sending and landing in `endpoint_reports`). No live production install yet in the deployment sense — this is still local unpacked-loading only; enterprise force-install policy configuration is documented but not configured (out of this task's scope).
**Key files:** `manifest.json` (MV3, `key`-pinned stable extension ID), `domains.js` (bundled allowlist, mirrors `paste_domains.go`'s `KnownPasteDestinations` exactly), `content-script.js` (paste capture + client-side hashing), `background.js` (durable buffer + native-messaging flush), `scripts/generate-key.sh`, `README.md`, `MANUAL_TESTING.md`.
**Interfaces:** native messaging only, to B0's `com.eami.agent` host — never a network call, never directly to `eami-api`. Message shape matches `eami-agent/internal/nativemsg.PasteEventMessage` exactly: `{type:"paste_event", destination_domain, occurred_at, content_length?, content_hash?}`.
**Data owned:** none server-side (stateless relay); locally, `chrome.storage.local`'s `eami_paste_buffer` key holds the durable send buffer (never the raw pasted text).
**Extension ID:** `ngmdfnecljeoleiancdedbmhjdihaoaa` — deterministic, derived from an RSA public key embedded in `manifest.json`'s `key` field (SHA-256 of the DER-encoded key, first 16 bytes, hex nibbles mapped a–p; this is Chrome's own documented algorithm, not a guess). Computed two independent ways (a shell/`openssl` script and an independent Go re-implementation) that agreed exactly. Stable regardless of install path or eventual Chrome Web Store publication (which assigns its own separate ID and doesn't read `key` at all). This same ID now replaces the `PLACEHOLDER_EXTENSION_ID_REPLACE_AFTER_B1` value in `eami-agent/internal/nmregister/nmregister_windows.go`'s `AllowedExtensionID` constant and the Linux/macOS postinstall scripts' embedded manifests.
**Design decisions:**
- **Bundled domain allowlist, not fetched** — no backend endpoint exists to serve it (`eami-api` frozen for this task, and no such endpoint exists regardless), and this matches the established convention of every other domain/extension allowlist in this codebase (`network_activity.KnownAIHosts`, `browser.knownExtensions`, `paste_domains.go` itself) — updated by hand with releases, documented as a manual-sync requirement (no automated enforcement that the three lists stay identical — a real, acknowledged gap, not hidden).
- **`chrome.alarms`, not `setInterval`**, for the periodic flush (1-minute period — Chrome's documented minimum for both packed and unpacked extensions since ~M120) — `setInterval` does not survive Manifest V3 service-worker suspension.
- **One native-messaging `Port` connection per flush, not one per event** — `chrome.runtime.sendNativeMessage`'s one-shot connect+send+disconnect would spawn a new `eami-agent-nmhost.exe` process per paste; batching through one `Port` avoids that.
- **Raw pasted text never leaves `content-script.js`**: `event.clipboardData.getData('text/plain')` is read into a local variable used only to compute `.length` and a `crypto.subtle.digest('SHA-256', ...)` hash, then goes out of scope. Every message-passing boundary (content script → background, background → native host) reconstructs a closed object literal with exactly the allowed fields — even a compromised/buggy upstream sender couldn't smuggle an extra field through, mirroring B-022/B-032's "closed field set, not a pass-through" convention. Verified in the actual shipped code by a mandatory security review, not just asserted by design (matching B-022's own standard).
**Verification — the native-messaging→backend leg, fully live and real:** with B0 re-registered using the real extension ID above, a message with the exact JSON shape `background.js` produces was sent through the **real, registered** `eami-agent-nmhost.exe` — invoked with **no `--config` flag**, relying entirely on the registry-based config fallback (`HKLM\SOFTWARE\EAMI\Agent`, ADR-014) exactly as a real MSI install would populate it, not a test-only YAML file — into a **real** `docker compose` Postgres/`eami-collector`/`eami-api` stack, and confirmed landing correctly in `endpoint_reports.report`'s `paste_events` array (`destination_domain`, `occurred_at`, `content_length`, `content_hash` all present and correct). This is the single riskiest, most novel integration point in this task and it is proven end-to-end with real code, not simulated.
**Verification — the in-browser leg (paste capture, injection scoping, storage durability):** **no browser-automation tool was available in this environment** (checked, confirmed absent). A first attempt to drive a real Chrome/Edge instance via `chromedp` (a genuine Go CDP library, fetched and initially working) was abandoned after it surfaced that this session's shell runs elevated, causing Edge/Chrome to silently de-elevate-relaunch themselves in a way that broke reliable flag/profile passthrough for automation — and, while investigating that, a blanket `taskkill /F /IM msedge.exe` was run that very likely killed the user's own real, unrelated Edge session, not just test instances (confirmed after the fact that none of the machine's running `chrome.exe` processes were test-created; Edge should restore its session on next launch via normal crash-recovery, but this was a real, avoidable mistake, disclosed to the user directly rather than glossed over). All further live-browser automation was stopped at that point. Instead: the extension's JS was syntax-validated with a real (pure-Go, zero-browser-risk) JS parser (`goja`), and every file was carefully read line-by-line against Chrome's documented MV3 API contracts (isolated-world execution, `chrome.storage.local` persistence semantics, `chrome.alarms` scheduling, native-messaging `Port` ordering guarantees cross-checked against B0's actual `RunHost` implementation) rather than assumed. A `MANUAL_TESTING.md` checklist is provided for the parts that genuinely need a human clicking through a real browser, honestly scoped to only what wasn't otherwise verifiable here.
**Reviewer + security subagent pass (mandatory, new browser-facing attack surface):** both ran independently. **Security review:** no-raw-content guarantee holds in the actual shipped code (traced, not assumed); permission scope (`storage`/`alarms`/`nativeMessaging` + 6 exact `host_permissions`, no `<all_urls>`) matches what the code does; one LOW-severity note (a compromised/XSS'd allowlisted page could dispatch a synthetic `paste` DOM event to forge fake telemetry — requires an attacker to already control JS execution on a trusted third-party AI-tool domain, a precondition far more severe than anything this extension introduces; not fixed, judged out of proportion given the precondition). **General code review** found one real, fixed issue: `background.js`'s original `chrome.storage.local` read-modify-write pattern (`bufferEvent`/`flush`) had a genuine lost-update race — two concurrent paste events (or a paste racing an in-flight flush) could both read the same pre-update buffer and the second `set()` would silently clobber the first's append, contradicting the file's own "never lose a buffered event" goal. **Interfaces — B-022 (2026-07-23), gateway tool credential encryption:** `POST /v1/gateway/tools` now actually persists the `credentials` object it was always documented (`api/openapi.yaml`'s `ToolCreate.credentials`) but never implemented — previously silently discarded (decoded, never read, never written to `gateway_tools.credentials_encrypted`, 201 returned anyway; a gap surfaced by a prior full-application audit, not previously tracked under its own B-ID). New package `eami-api/internal/toolcreds` (`toolcreds.go`) implements AES-256-GCM encrypt/decrypt with a hex-encoded 32-byte key (`TOOL_CREDENTIALS_ENCRYPTION_KEY` env var, `config.Config.ToolCredentialsEncryptionKey`) — encryption happens in the API process; Postgres never sees the key or the plaintext. Deliberately not pgcrypto (the column's own schema comment says "encrypted using pgcrypto," but that extension is otherwise unused anywhere in the codebase — using it would mean sending the key to Postgres as a query parameter on every write, a weaker posture than app-side AEAD). `Server` gets a `toolCreds *toolcreds.Cipher` field (nil if the key is unconfigured — optional at startup, same convention as the B-002 gateway proxy config) and a `toolStoreOverride`/`toolQueries()` test seam scoped to `tools.go` only (mirrors `storeIface`/`WithGatewayClient` elsewhere in this file, doesn't touch the broader `Store` interface). `CreateTool` decodes `credentials` as `json.RawMessage` and a `credentialsProvided` helper decides presence structurally (any JSON object with ≥1 key, regardless of key names) rather than via the typed `ToolCredentials` struct — this was a security-review-caught bug in an earlier version of this change: deciding presence via the typed struct meant any unrecognized field name (a typo, a future field) decoded to an all-empty struct and silently reproduced the exact bug being fixed. The raw submitted bytes are what gets encrypted and stored, not a re-marshaled struct, so nothing the client sends can be dropped by the struct's fixed field set. If credentials are submitted but no key is configured, the request fails closed (500, no store call, no tool row created) — never a silent-success-with-data-loss. Credentials are write-only: `store.GatewayTool`/`ToolResp` have no field for the encrypted blob, and no query in `tools.sql.go` selects `credentials_encrypted` back out, so there is no leak surface in `ListTools`/`CreateTool`'s responses (structurally, not just by convention).

**Interfaces — B-023 (2026-07-24), real `TestTool` connectivity check:** `POST /v1/gateway/tools/{toolId}/test` no longer returns a synthetic "connected" result — it was a stub (`tools.go`'s old comment: "For now returns a synthetic 'connected' result after a brief probe" — there was no probe). New file `eami-api/internal/api/tool_connectivity.go` performs a real check per `type`: `rest_api` does a real `http.Client` GET to `base_url` (`Authorization: Bearer <api_key>` if present, HTTP Basic using `oauth_client_id`/`oauth_client_secret` as a best-effort fallback for non-standard "OAuth" APIs that accept it, `auth_type=basic` always reports `misconfigured` since `ToolCredentials` has no username/password fields to supply it) — 401/403 classify as `auth-failed`, any other completed response (including 4xx/5xx) as `connected` (reaching the server and getting *a* response proves DNS/TLS/network work, which is what the test is actually asserting). `database` does a real `pgx.ConnectConfig` handshake against `connection_string` — a successful connect already proves both reachability and valid credentials (Postgres's own auth happens during the handshake), and a failure is classified via SQLSTATE: class `28xxx` (`invalid_password`/`invalid_authorization_specification`) → `auth-failed`, anything else → `unreachable`. `mcp` always reports `misconfigured` with an explanatory message: `mcp_command` describes a local subprocess meant to run on the gateway host, not eami-api's cloud process — executing an admin-supplied command string from the SaaS backend would itself be a command-injection/RCE surface, and `eami-gateway/internal/proxy` (read for this task) confirmed the gateway's real dispatch path doesn't even consult `gateway_tools` per-tool either, so there's no existing per-tool MCP connection behavior to mirror. Every outcome is bounded by an 8-second context timeout (`toolTestTimeout`) applied once, wrapping both the decrypt step and the dial — no retries, per this task's scope. Response shape changed from the old stub's `{status, latency_ms}` to `{success, latency_ms, error}`, which is what `api/openapi.yaml` has documented for this route all along (another previously-undetected spec-vs-implementation mismatch, now closed). The richer 4-way outcome (`connected`/`auth-failed`/`unreachable`/`misconfigured`) is only in the HTTP response — `gateway_tools.status`'s DB `CHECK` constraint only allows 3 values (`connected`/`degraded`/`disconnected`, schema frozen, not touched by this task), so `toolTestOutcome.dbStatus()` maps `auth-failed` → `degraded` (reached the endpoint; credentials are what's wrong) and both `unreachable`/`misconfigured` → `disconnected` for the persisted column only.

**Security-critical addition, found by review, not in the original plan:** `eami-api` is EAMI's own cloud SaaS backend (per `ARCHITECTURE.md`), architecturally distinct from `eami-gateway`, which runs on-prem inside the customer's own network. Without a network-target guard, an org-scoped `admin`/`operator` (a role with no other legitimate reach into EAMI's cloud environment) could point a tool's `base_url`/`connection_string` at cloud metadata endpoints (`169.254.169.254`) or internal-only services and use the connected/auth-failed/unreachable distinction as a reachability oracle against EAMI's own infrastructure — a real boundary crossing this feature would otherwise introduce, not a restatement of capability the caller already has via `eami-gateway` (which runs *in* the customer's own network, where they already have legitimate reach). Added `safeDialContext` + `isBlockedTestTarget`: resolves the target host (or parses it directly if already an IP literal), rejects the request before dialing if *any* resolved address is loopback, link-local (covers `169.254.169.254` and `fe80::/10`), unspecified, or private/RFC1918/ULA (via Go's own `net.IP.IsLoopback`/`IsPrivate`/`IsLinkLocalUnicast`/`IsLinkLocalMulticast`/`IsUnspecified`), then dials the already-validated IP directly (not the original host) so a DNS answer that changes between the check and the actual connection (rebinding) can't slip through. Wired into both paths: `testRESTTool` via `http.Transport.DialContext`, `testDatabaseTool` via `pgx.ParseConfig` + `cfg.DialFunc` + `pgx.ConnectConfig` (replacing the simpler `pgx.Connect(ctx, connString)`, which has no dial-level control point). Security review re-verified the fix clean, tracing the `169.254.169.254`/RFC1918 cases end-to-end through the real (non-test) code path and confirming the new `Server.toolDialOverride` test-injection seam (needed so tests can exercise real round-trips against local `httptest` servers, which the guard would otherwise correctly reject) is assigned only in `_test.go` files — never reachable from any HTTP request.

**Other fixes from the general code-review pass, applied before commit:** (a) `safeDialContext` originally only dialed the first resolved address; fixed to fall back through every validated address in order, mirroring `net.Dialer`'s own multi-address behavior — a host whose first A/AAAA record is down but whose second works no longer incorrectly reports `unreachable`. (b) `testRESTTool`'s per-call `http.Transport` had keep-alives enabled with nothing ever calling `CloseIdleConnections()` — since the ad-hoc Transport is discarded after each call but the underlying connection and its `readLoop`/`writeLoop` goroutines stay reachable through the open connection itself, every `TestTool` call against a REST tool leaked one idle socket/goroutine; fixed with `DisableKeepAlives: true` (a one-shot connectivity check has no reuse benefit anyway). (c) `testDatabaseTool`'s deferred `conn.Close(context.Background())` had no deadline of its own — if the peer went unresponsive after a successful handshake, `Close` could hang past the 8s bound the rest of the design promises; fixed with a dedicated 2-second close-only context, independent of the (possibly already-expired) outer context.

**Credentials never leak, first production `Decrypt` caller:** a new `toolStore` interface method, `GetToolForTest`, is the only place `credentials_encrypted` is ever read back — implemented via `toolStoreWithConnectivity`, a thin wrapper running one raw SQL query through `s.queries.DB()` (the same escape hatch `finops.go` already uses for queries with no sqlc-style wrapper), so `eami-api/internal/store/tools.sql.go` needed zero changes (explicitly confirmed acceptable with the user before implementing, since it's a deviation from this codebase's usual sqlc-style convention). The decrypted plaintext only ever reaches an `Authorization` header or a Postgres connection string — `classifyHTTPError`/`classifyPgConnectError` return only static, categorical strings (`"timed out"`, `"connection failed"`, `"database rejected the credentials"`), never `err.Error()` on the underlying error, which could otherwise echo back request/DSN details. `toolcreds.Decrypt` failures (wrong/rotated key, corrupted blob) are a clean `misconfigured` result, never a panic, never exposing the underlying decrypt error text.

**Security-review-caught bug, fixed before commit:** the first version of `dsnHasPlaceholderPassword` did a raw `strings.Contains(lower, ":changeme@")`-style substring check directly against the whole DSN, with no trimming. `isPlaceholderSecret` (used for `ServiceKey`) already trimmed whitespace, but this sibling function didn't — so `API_DB_PASSWORD=" changeme"` (leading space) or `API_DB_PASSWORD="changeme\r"` (a CRLF-corrupted `.env` value — this repo has already hit a real CRLF bug once, see B-020) would build a DSN like `...: changeme@host...` or `...:changeme\r@host...`, and the un-trimmed substring check would miss it, silently starting with an effectively-default password. **Interfaces — B-026 (2026-07-24), persistent RSA key for user-session JWTs:** `internal/auth/auth.go`'s RS256 signing key **regenerated in memory on every container restart in the actual running system** — not because no persistence mechanism existed in the code (`NewService` already had a `loadPrivateKey` path for a non-empty `keyPath`), but because `internal/config/config.go` had **no env-var override for `cfg.Auth.RSAPrivateKeyPath` at all**, and neither `eami-api.yaml` (ships `rsa_private_key_path: ""`) nor `docker-compose.yml`/`.prod.yml` set one — so the docker-deployed system was always in ephemeral dev-mode, force-logging-out every user on every restart. Mirrors `eami-gateway/internal/identity`'s `loadOrGenerateKey` pattern (read as the reference implementation, not modified by this task): new `loadOrGenerateKey(path string) (*rsa.PrivateKey, error)` in `auth.go` tries the existing `loadPrivateKey` (unchanged — still supports both PKCS1 `"RSA PRIVATE KEY"` and PKCS8 `"PRIVATE KEY"` PEM formats, a bit more flexible than gateway's PKCS1-only loader), and only if the error is specifically `os.ErrNotExist` (checked via `errors.Is`, correctly unwraps through `loadPrivateKey`'s `%w`-wrapped `fmt.Errorf`) generates a new 2048-bit key, `os.MkdirAll`s the parent dir (`0700`), and writes PKCS1-PEM at `0600`. ## Cross-cutting / shared
- **Postgres backup & disaster recovery (B-029, 2026-07-25):** no backup mechanism existed at all before this — `docker compose down -v` or disk loss was unrecoverable, a real gap for a product whose core value is an immutable audit trail. `scripts/reseed.sql` (a demo-data convenience script) was headed "Re-seed org and admin user after `docker compose down -v`," easy to mistake for real recovery — it only recreates one org/user, not any prior data.
  - **Mechanism:** new `eami-backup` service in both `docker-compose.yml`/`.prod.yml`, image `postgres:16-alpine` (has both `pg_dump` for PG16 and Alpine's busybox `crond`). Investigated `pg_cron` first (already running in the `postgres` container, used for `audit_log` partitioning — `schema/migrations/007`) but rejected it: `pg_cron` jobs execute as SQL inside the Postgres backend and can't shell out to run an external client program like `pg_dump` to write a file — that needs a real separate client process. New `scripts/backup-db.sh` (POSIX `sh` — the container has no bash) runs `pg_dump -Fc` to a `.tmp` file, atomically `mv`s it into place only on success, logs a timestamped line either way, exits non-zero with a clear `ERROR` line on failure (never silent), and prunes down to `BACKUP_RETENTION_COUNT` (default 14) newest dumps, also sweeping any orphaned `.tmp` files from a previously killed run. New `scripts/backup-entrypoint.sh` installs a real crontab (`BACKUP_SCHEDULE`, default `0 3 * * *`) and `exec`s `crond -f -l 2`, handling two dockerized-cron gotchas that would otherwise make this silently non-functional: `crond` doesn't pass the container's env through to jobs (captured into a `chmod 600` sourceable file instead, values POSIX-single-quote-escaped so a literal `'` in a hand-typed password can't corrupt the file), and `crond` job output doesn't reach `docker logs` by default (redirected into the container's own PID 1 fds, `/proc/1/fd/1`/`2`). Validates `BACKUP_SCHEDULE` has exactly 5 fields before installing it (falls back to the default + logs an `ERROR` rather than silently never firing again on a typo), and runs one backup immediately at container start so a fresh deployment has a baseline backup within seconds rather than waiting up to a full schedule interval.
